# 工程规范（对所有项目生效）

> 来源：用户明确要求 —— 代码要**结构化、模块化**，不要把功能全堆在一个界面/一个文件里；
> 能单独命名拆出来的就单独拆；要有**数据结构、设计模式、继承**；还要**考虑性能**。
> 本条规范对之后所有项目都适用。

## 1. 文件与模块

- **一个界面 / 一个职责 = 一个文件**。不允许把 500 行以上的界面逻辑塞进单文件；超过就按职责拆（数据层 / 算法层 / 渲染层 / 交互层 / 视图层）。
- 文件命名用职责名（`editor`、`renderer`、`viewport`、`history`），不要用 `utils2`、`misc`、`common` 这类垃圾桶名字。
- 依赖方向单向：底层（工具/数据结构/算法）不得反向依赖上层（DOM/界面）。
- 入口文件只做**装配**（初始化顺序、模块接线），不写业务逻辑。

## 2. 数据结构与状态

- 可变状态**集中在一处**（如 `state.js`），并注释每个字段含义；不允许散落成几十个模块级全局变量各改各的。
- 能用**类/结构体**表达的概念就用类表达（`History`、`Viewport`、`Grid`、`Tool`），不要用裸数组 + 一堆约定。
- 大数组用 TypedArray；缓存的键要明确（WeakMap 以对象为键、字符串 key 要带版本）。

## 3. 设计模式与继承

按场景选，不要为用而用，但**该抽象时必须抽象**：

| 场景 | 用什么 |
|---|---|
| 多种互斥操作（画笔/橡皮/填充/取色） | 策略模式 + 基类继承（`Tool` → `PaintTool` → `Brush/Eraser`） |
| 固定流程、步骤可变 | 模板方法（`Pipeline.run()` 固定阶段，阶段实现可换） |
| 对象创建分散 | 工厂（`createGridTool(name)` + 注册表） |
| 撤销/重做、状态恢复 | 命令/备忘录（`History` + 快照或差量补丁） |
| 跨模块通知 | 事件/订阅（避免直接互相调用造成环） |
| 只有一份的全局服务 | 单例实例（`viewport`、`perf`、`perf`） |

- 继承只用于**真正的 is-a 关系**（橡皮是画笔的一种行为），组合优先于深层继承（不超过 2 层）。
- 新增同类能力时，优先"注册表加一行"，而不是"到处改 if/else"。

## 4. 性能

- 高频路径（`pointermove`、`input`、`resize`）必须 **防抖或按帧合并**（`debounce` / `rafThrottle` / rAF 重绘）。
- **缓存**：离屏画布、色板转换、布局矩形；缓存必须显式失效（`patDirty`、`invalidatePreviewRect()`）。
- **避免强制同步布局**：拖动/悬停期间不要反复 `getBoundingClientRect()`，读一次缓存。
- 重计算分层：改一个格子不该重跑整条管线；参数没变不要重算（dirty 标志）。
- 每帧预算 16.7ms：关键流程要有计时（`PerfMeter`），并在界面上可见；性能回归要能被发现。
- 上万次循环里避免对象分配（用 TypedArray / 复用数组），避免字符串拼接做 key。

## 5. 可维护性

- 断言式注释：每个文件顶部一句话说明职责；每个公开函数注明输入输出与副作用。
- 命名即文档：`buildBgMask` / `mergeSimilarColors` / `zoomAt` 比 `doIt` / `helper` 好一百倍。
- 配置与数据外置（色板、尺寸模板、板规格），不要写死在逻辑里；数据文件单独一个（如 `palettes.js`）。
- 有 UI 状态机的地方要能**往返**（面板开/关、步骤切换），关闭路径必须完整（点击遮罩 / Esc / 收起按钮）。
- 破坏性操作（清空编辑、重排版）要有提示，或提供撤销。

## 6. 交付检查清单（每次提交前）

- [ ] 没有超过 ~400 行的界面文件；职责能一句话说清。
- [ ] 新状态写在 state 层，有注释；没有新增散落的全局变量。
- [ ] 高频事件有防抖/节流；重绘有缓存与脏标记。
- [ ] 新增能力优先走注册表/基类，而不是改多处 if/else。
- [ ] 浏览器实测通过（含移动端视口），无运行时报错。
- [ ] 相关文档（架构/README）与离线缓存清单（Service Worker）同步更新。
