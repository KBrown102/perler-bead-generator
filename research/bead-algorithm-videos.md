## 1. 结论先行（TL;DR）

1. **社区共识的流水线是 4 步**：① 转成"合适的像素尺寸" → ② 处理轮廓 → ③ 颜色收敛并确认品牌色号 → ④ 统计每种颜色/总豆数。B 站"拼豆世界"作者自述、多个生成器工具的功能列表都收敛到这条链路。✅
2. **"糊"的第一主因不是分辨率不够，而是采样方式错了。** AI 生成的"像素风"图常是**伪像素网格**（格子大小不一、发虚、带抗锯齿过渡色），任何双线性缩放都会把过渡色混进来，量化后自然碎。✅（B 站 UP「一次黑夜」把这三件事命名为"伪像素网格 / 色彩污染 / 边缘柔化"）
3. **业界有一个现成的解法**：FFT 检测网格周期 → Sobel 边缘微调对齐 → **majority/median 取样**（而非插值）。开源项目 Perfect Pixel 的 README 明说："Standard scaling often fails … due to inconsistent sizes and non-square grids"，其 API 里 `sample_method = center | median | majority`。✅
4. **社区基本不用抖动（dither）。** 明确的工程化表述出现在 Perfect Pixel 给生成模型的提示词里："no gradients, no shading, no lighting, **no dithering**, no texture. No anti-aliasing or smoothing — every pixel must be a perfect square bead aligned to the grid." ✅ 这条与我们当前默认开抖动/平滑直接冲突。
5. **颜色不是"越少越好"，而是"够用且可买"。** 一猹（B 站画图纸 UP）原话：图纸**221 色**，**144 色差别也不会特别大**，主要看冷门色；画图用 188 的电子色卡，"只能确保 221 色能覆盖"。热评则说 96 色明显不够、建议直接买 200+ 的补色包。✅
6. **尺寸有行业惯例**：小板 **52×52**、大板 **78×78**（定制报价按此计价）；抖音图纸文案常见"尺寸:40""52*52 板子可拼""50×61 格""30 颗豆以内"；豆径有 **2.6mm 迷你豆**与 5mm 常规豆。✅/🟡
7. **描边是显式选项**：B 站专栏作者做同一张图会出"**有黑边/无黑边两个版本**"；Perfect Pixel 的提示词要求"clean, continuous dark outline"。✅
8. **亮度/对比/饱和有争议**：有实操者（腾讯云征文）明确说把"原始色改**暖调提亮**"是四轮返工中的关键一步；也有画图纸 UP 主强调颜色要按色卡来、冷门色会翻车。结论：**可以做，但必须"轻微 + 量化前 + 量化后复核色号"**，不能默认自动加。✅/🟡

## 3. 方法论提炼（重点）

### 3.1 被反复确认的 4 步流水线

```
选图 → ① 定"像素尺寸"（几格） → ② 轮廓（去背景 / 描边 / 硬边）
     → ③ 颜色收敛 + 品牌色号匹配 → ④ 豆数统计 + 打印/A4/分板
```

证据：拼豆世界作者自述（✅）、我赞拼豆"三件事"（🟡）、方块工坊功能列表（✅）、bitbead/徐小豆功能列表（✅）。
**我们当前管线（`src/pipeline.js`）是**：采样 → 限色 → 量化(+抖动) → 并色 → 平滑 → 去杂色/描边 → 出图。
差异在于：社区把"**定尺寸**"和"**轮廓**"当作一等公民，我们把它们散落在参数面板里；社区不做"平滑"，我们默认有。

### 3.2 网格尺寸怎么定

社区没有统一的"公式"，但有稳定的**场景-格数-板材**对应关系（综合 ✅ 参数与 🟡 文案）：

| 用途 | 建议格数（长边） | 对应实物（5mm 豆） | 依据 |
|---|---|---|---|
| 迷你挂件 / 钥匙扣 / 冰箱贴 | **12–20 格**（"30 颗豆以内"属于极简款） | 6–10 cm | 抖音"尺寸:40"应为含多块小板的大图口径（⚪ 推断）；B 站"7cm 钥匙扣"视频标题（[BV1AS4y1f73K](https://www.bilibili.com/video/BV1AS4y1f73K)，✅ 标题）暗示 14 格 ≈ 7cm |
| 常规挂件 / 小摆件 | **20–32 格** | 10–16 cm | Perfect Pixel 推荐 16×16 / 32×32（✅） |
| 摆台 / 装饰画（单板） | **40–52 格** | 20–26 cm | 行业小板 **52×52**（✅ 报价简介）、抖音"尺寸:40"（🟡） |
| 大图 / 多板拼 | **78–104 格**（78×78 = 大板，需拼板） | 39–52 cm | 报价"78*78 的 20r"（✅）、抖音"50×61 格"（🟡） |
| 细长条（眼睛条/字牌） | 30×60 这类非方比例 | — | ✅ 报价简介原文 |

**关键提醒**：社区抱怨的"转换出来豆量特别多、每个都是两三个板大小"（✅ 热评），本质是**默认输出格数按图片分辨率走**，而不是按"用途→尺寸"反推。我们的 UI 应该**先问用途/成品厘米数，再反推格数**，而不是让用户拖一个 0–200 的滑块。

**尺寸换算（我们应直接显示）**：
`成品宽 cm = 格数 × 豆径`（迷你豆 2.6mm、常规 5mm）×（熨烫收缩 ~0–5%，⚪ 经验值）  
`需要板数 = ceil(格宽/52) × ceil(格高/52)`（52×52 小板；78×78 大板同理）

### 3.3 颜色怎么减（限色 / 并色 / 色号）

**社区的经验值（✅ 均出自原文）**：
- 图纸色数**按 221 色系画**，**144 色"差别也不会特别大"**，真正卡人的是**冷门色**（超低饱和、多层次黑/白、多层次彩）。
- 新手买**基础包**就够；但 **96 色明显不够**（热评原话"96 色颜色都缺"），认真做建议 **200+ 补色包**。
- 实物有**批次色差**（"补的豆子有色差"、"色差小到熨完才看出来"）→ 色号匹配再准也有上限，必须有**缺色替换表**兜底。

**减色的工程做法（综合 ✅ 工具自述 + ⚪ 推导）**：
1. **两级颜色**：先把整图颜色收敛到"N 色工作色板"（`减色方案`，方块工坊自述有"更多样化的减色方案"✅），再逐格映射到**品牌色卡**（Perler/Hama/Artkal/MARD）。
2. **保护色**：黑（描边）、白（高光/背景）、主色 top-3 **不允许被并掉**。⚪（推导；依据是"色彩污染"与"描边"两个已验证现象）
3. **并色阈值用感知色差**（OKLab/CIEDE2000 的 ΔE），不要用 RGB 欧氏距离——RGB 距离会把"看起来完全不同"的色判为相似。⚪（我们代码里 `src/color.js` 已有 OKLab，方向对）
4. **限色数量建议**（⚪ 综合推导，非某位 UP 原话）：

| 图幅 | 建议工作色数 | 说明 |
|---|---|---|
| ≤20 格（钥匙扣） | **6–10** | Perfect Pixel 提示词给的是 6–8（✅），与"极小图必须概括"一致 |
| 20–32 格 | **10–16** | 再多会出现"单颗孤豆"，肉眼即噪点 |
| 32–52 格 | **16–24** | 一猹的"144 色差别不大"是在此区间之上的经验 |
| >52 格（大图） | **24–40** | 上限由色卡决定（221 色内） |

5. **"合了颜色还是一堆颜色"是真实 bug 报告**（✅ 一次黑夜视频热评原话：`明明已经合并了颜色，为啥还是一堆颜色的呢?`）→ 说明**减色必须做"最终色数统计 + 未使用色清理 + 视觉验证"**，不能只信算法里的 k。

### 3.4 抖动（dither）：社区答案基本是"不要"

- ✅ 直接证据：Perfect Pixel 提示词 "**no dithering**"；"no anti-aliasing or smoothing"。
- ✅ 间接证据："色彩污染"被列为三大天坑之一；"色差小到熨完才看出来"说明用户对**单格色**极其敏感，抖动产生的棋盘格会让"色号清单"翻倍。
- ⚪ 推导：拼豆是**离散色块**，抖动的收益（视觉近似）远小于代价（颜色数↑、返工↑、单颗孤豆↑）。

👉 **建议**：抖动保留为"高级/实验"开关，**默认关闭**；开启时给出"预计用色数将增加 X 种"的预警（这个数字我们能算）。

### 3.5 边缘 / 轮廓 / 去背景

三条社区实践（均有出处）：

1. **满格 → 异形**（去背景）：腾讯云实作"满格改异形"，豆量 1728→1304（**−24.5%**）✅。异形的含义是**背景格 = 无豆/空豆**，而不是白豆。
2. **描边是显式开关**："有黑边/无黑边两个版本"✅；Perfect Pixel 要求"**clean, continuous dark outline**"（连续、闭合、深色）✅。
3. **主体居中 + 四周留 1–2 行空豆**（Perfect Pixel 提示词 ✅）——不是算法问题，是**上板可操作性**：边缘贴边会让熨烫/转移失败。

**反向证据（很重要）**：像素画里的"手工抗锯齿"是有意的美术风格（✅ 沉思虎视频），所以**不能默认对所有输入都"去抗锯齿"**；但对"AI 生成的伪像素图"，去抗锯齿=颜色干净。判别依据应该是**网格周期性**，不是"看起来像像素"。

### 3.6 亮度 / 对比 / 饱和 到底要不要调

- **"要调"的一侧**（✅ 腾讯云实作）："原始色改**暖调提亮**"是四轮返工的关键动作之一——因为屏幕上的冷白/灰白，做成实物豆会显脏。
- **"别乱调"的一侧**（✅ 一猹）：画图**对着电子色卡**（188 色）来，**只用能买到/能覆盖的色号**；调色若把颜色推离色卡，最后还得硬映射回去，等于白调。
- **"调了也白调"的一侧**（✅ 热评）：实物**批次色差**、补豆色差，最终成品色差可能大于调色带来的收益。
- ⚪ 我们的结论：**分输入类型**
  - 像素画 / 已有色号的图：**禁止自动色调增强**（会破坏 1:1 色号）；只允许手动、且在量化前。
  - 照片 / 插画：可以提供 **±（亮度/对比/饱和度）温和预设**（建议幅度 ≤10%），**在量化之前**应用，并在应用后重新计算色号与豆数；UI 要明确写"会影响最终色号"。

### 3.7 像素画 / 像素风图片怎么 1:1 转拼豆（我们的核心痛点）

**问题定义（社区已命名）**：AI 生成的"像素风"图 = **伪像素网格**：格子大小不一、边界发虚、带半透明过渡色（✅ 一次黑夜）。
**为什么常规缩放会糊**：非整数倍缩放会把过渡色摊到多个格子里 → 量化后每格颜色都不对 → 视觉"碎、脏、糊"（✅ + ⚪）。

**可落地的算法（照抄 Perfect Pixel 三步，✅ 原文）**：
1. **FFT 幅值检测网格周期**（得到格子大小 grid_w/grid_h；`min_size`、`peak_width` 控制灵敏度）。
2. **Sobel 边缘**做格线微调对齐（`refine_intensity ∈ [0, 0.5]`）。
3. **逐格取样**：`sample_method = majority`（或 `median`），**绝不用 bilinear/area 平均**。

**判定与分支（我们要加的策略，⚪ 工程推导）**：
```
检测网格周期 p（x/y 方向分别算，允许不等比）
若 p≈1（图本身就是 1px=1格）:
    → 直通模式：1 豆 = 1 像素，不做任何缩放；
      只做「品牌色号映射 + 可选去背景 + 可选描边」
若 p 为整数 >1（例如源图是 8×8 放大的）:
    → 每 p×p 块取众数 → 得到 native (W/p)×(H/p) 网格 → 直通
若 p 非整数 / 检测失败:
    → 用「area-majority」按目标格数取样（每格内像素投票）
    → 或提示用户：这张图不是真像素画，建议用「照片模式」
```
**关键约束**：目标格数**不得非整数倍地缩小**像素画。65×70 的像素画：
- 若板子放得下 → **输出 65×70 直通**（= 65×70 颗豆，5mm 豆约 32.5×35 cm，需 2×2 块 52 板）；
- 若要更小 → 优先 **整数降采样 k=2 → 33×35**（或裁切），**不要** 65→52 这种 0.8 倍重采样；
- 若要更大 → **整数倍 nearest 放大**（每格 N×N 同色），保持硬边。

**这条与我们现状的关系**：`src/image.js` 已有 `detectPixelBlock` + `snap` 采样 + `analyzeSource` 的"像素风"判定（`flatness ≥ 0.55 && w≤150 && h≤220`），方向是对的；但
- `flatness` 是**启发式**，带抗锯齿的像素画 flatness 会掉到阈值以下 → 误判成照片；
- 建议换成**网格周期检测**（FFT/自相关/行程长度 GCD）作为主判据，flatness 只作辅助；
- `downsample()` 在 `sampleMode==='average'` 时用 canvas 双线性（`imageSmoothingEnabled = true; quality='high'`），**这正是"糊"的来源**，需要补一个 **majority 采样器**。

### 3.8 常见"翻车点"清单（带来源）

| 现象 | 真实成因 | 来源/置信度 |
|---|---|---|
| 图纸糊、边缘发虚 | 采样用了插值/平滑；源图带抗锯齿过渡色 | ✅ 一次黑夜（三坑）；⚪ 工程解释 |
| 颜色碎、色号一大堆 | 量化到整张色卡而非"工作色板"；减色阈值用 RGB；抖动 | ✅ 热评"合了还是一堆颜色"；⚪ 归因 |
| 豆量爆炸、要拼两三块板 | 输出格数按图片分辨率走，没按用途反推 | ✅ 热评原文 |
| 成品和屏幕不像/脏 | 屏幕 sRGB vs 实物豆色差；冷白/灰白实物偏脏；批次色差 | ✅ 一猹、色差视频、热评 |
| 缺色、买不到 | 图纸用了冷门色（超低饱和/多层次黑） | ✅ 一猹、李猫儿替换表 |
| 背景留白豆（大白底） | 未去背景，背景被量化成白豆 | ✅ 腾讯云"满格改异形" |

| 熨完才发现色差 | 颜色相近的两种豆在未熨时更难区分 | ✅ 10 大崩溃瞬间热评 |

## 5. 与当前实现的差异（读 `src/pipeline.js` / `src/image.js` 得出）

| 现做法 | 社区做法 | 冲突程度 |
|---|---|---|
| `downsample()` 在 `average` 模式用 canvas **双线性 + preSmooth** | 明确 **禁止平滑/AA**，必须 **majority/median** 取样 | 🔴 高（直接造成糊） |
| 量化阶段默认带 **dither（含 kernel/strength）** | **no dithering**；抖动会让色号清单爆炸 | 🔴 高 |
| 量化后还有 **`modeFilterGrid` 平滑** | 社区追求"硬边、干净色块" | 🟠 中（照片或许有用，像素画必关） |
| 像素画判定 = `flatness ≥ 0.55 && ≤150×220` | 判定应基于 **网格周期**（FFT/Sobel） | 🟠 中（带 AA 的像素画会误判） |
| 描边颜色 = **色板里最深的颜色** | 应为 **黑/深中性色**，且只描**外轮廓** | 🟠 中（浅色图会变成"彩色描边"） |
| 参数面板以"格数滑块"为主 | 应先选**用途/成品厘米**再反推格数，并显示板数/豆数 | 🟠 中（UX 层） |
| 无"成品 cm / 需要几块板 / 每色豆数"换算 | 社区高频问题，竞品均提供 | 🟠 中 |
| 已有 `detectPixelBlock` + `snap` + "1:1 还原"按钮 | 方向一致 ✅，但应**自动**触发，别让用户找按钮 | 🟢 低（增强） |
| 已有 OKLab 色差（`src/color.js`） | 方向正确 ✅ | 🟢 一致 |

## 6. 对我们生成器的可执行建议

### A. 立刻能改的算法 / 默认参数

| # | 改动 | 怎么改（落点） | 预期效果 |
|---|---|---|---|
| A1 | **新增 majority 采样器，并设为像素画默认** | `src/image.js > downsample()`：对每个目标格，收集其覆盖的源像素，按 alpha 加权投票取众数色（可先量化到 16 色再投票）；`sampleMode` 增加 `'majority'` | 直接消掉"糊边/串色/新中间色"，边缘变硬 |
| A2 | **网格周期检测替代 flatness 判定** | `ensureSnapInfo()` 里把 `detectPixelBlock` 升级为：行/列方向求"相邻同色行程长度"的 GCD + 自相关峰值，得到 `(px, py)`（允许非等比）；`p≈1` 即 1:1 | 带 AA 的 65×70 像素画也能被正确识别，不再走重采样 |
| A3 | **1:1 直通自动生效** | 检测到 `p≈1` 或 `p` 为整数时，自动把 `gridW/gridH` 设为原生格数并锁定，UI 显示"已 1:1 还原（可改）" | 65×70 像素画 1:1 输出，零信息损失（当前需手动点按钮） |
| A4 | **非整数倍缩放时禁止插值** | `downsample()` 里 `imageSmoothingEnabled=false`，改走"面积众数"，并在不匹配时提示"建议裁切或整数倍缩放" | 消除 0.8×/0.67× 这类最伤的缩放 |
| A5 | **抖动默认关闭** | `state.js` 默认 `useDither=false`；像素画模式强制关；开启时 UI 显示"预计用色 +N 种" | 颜色碎的问题立竿见影；色号清单不再翻倍 |
| A6 | **平滑（mode filter）默认 0 次** | 像素画模式强制 0；照片模式保留但默认 1 次以下，并标注"会软化边缘" | 边缘硬、色块整 |
| A7 | **描边颜色改为"黑 / 最深的低饱和色"，只描外轮廓** | `src/outline.js`：候选色限于 `L* < 25 且 C* < 15`（OKLab）；先做主体 mask（非背景连通域）再取形态学外边界，不做内部同色边界 | 浅色图不再出现"彩色描边"；轮廓闭合可读 |
| A8 | **限色保护色 + 分档默认值** | `src/quantize.js > buildReducedPalette()`：先锁定 黑/白/主色 top-3，再对剩余色做 k-means/中位切分；默认值按图幅分档 8 / 12 / 20 / 32 | 少出现"合了还是一堆颜色"；颜色数符合场景 |
| A9 | **输出面板加"成品尺寸 / 板数 / 总豆数与每色豆数"** | `src/legend.js` + `exporter.js`：`cm = 格 × 豆径`（2.6/5mm 切换）、`板数 = ceil(w/52)×ceil(h/52)`、每色豆数排序 | 直接回答评论区最高频的三个问题，提升"可落地感" |
| A10 | **去背景 → 异形（空豆）而非白豆** | 从图像四边 flood fill（容差 ΔE）+ alpha=0 区域；背景格标记为"无豆"，统计里扣除；提示"省 X 颗豆" | 对齐"满格改异形 −24.5%"的实践，白底图不再浪费豆 |
| A11 | **照片模式才提供温和色调预设** | 在量化前应用 亮度/对比/饱和（幅度 ≤10%），应用后重算色号；像素画模式隐藏该入口 | 避免破坏 1:1 色号，同时满足"暖调提亮"需求 |
| A12 | **色号偏差提示 + 缺色替换** | 若某色在目标品牌色卡中 ΔE 过大（>8），标记"⚠ 近似色"，并提供"替换表"入口（可导入社区替换表） | 减少"吸色对不上"的售后问题 |

### B. 需要评估的（先做实验，不要直接上线）

| # | 议题 | 评估要点 | 预期收益 |
|---|---|---|---|
| B1 | **FFT 网格检测的鲁棒性** | 在 200 张真实社区图纸（含 AI 生成、PS 马赛克、手绘格子、带水印）上测 `p` 的召回/误判；对比"行程 GCD"与"FFT 峰值"两种实现 | 决定 A2 是否可替代 flatness |
| B2 | **限色数量 vs ΔE 阈值的最优组合** | 用"用色数 / 与手工图纸的色块一致率 / 主观干净度"三指标做网格搜索 | 找到每档图幅的最佳默认值，替代拍脑袋 |
| B3 | **抖动是否要保留** | A/B：同图开/关抖动，看"色号数、孤豆数、用户返工率"；照片类可能有人喜欢颗粒感 | 决定是否彻底移除或仅隐藏 |
| B4 | **非整数倍场景的处理策略** | "裁切 vs 整数倍降采样 vs 加边"三种，哪种用户更接受；建议做成三选一而非自动 | 避免"65→52"这类不可逆损伤 |
| B5 | **自动抠图质量** | 简单 flood fill vs AI matting（人像/宠物/发丝）的成本与效果；失败时回退"满格+手动橡皮" | 决定是否引入模型 |
| B6 | **跨品牌色号转换与屏幕色差补偿** | MARD ↔ Perler/Hama/Artkal 官方对照表的准确性；是否要提供"实物色卡拍照校准" | 提升"出图即能买豆"的闭环 |
| B7 | **大图分板 + A4 打印排版** | 分页处加坐标 + 色号图例 + 重叠 1 行；与竞品（方块工坊/拼豆世界）对比 | 大图场景留存 |

## 7. 局限与后续可补

1. **B 站视频"讲了什么"只能靠简介与热评**：我们有标题/简介/热评，但**没有逐字稿**（AI 字幕接口需登录）。所以"UP 主在视频里说'颜色控制在 X 色内'"这类**口播参数无法核实**——本报告没有编造任何此类转述。
2. **知乎/小红书/贴吧正文全部 403**：这三处很可能是"手工画图纸"方法论最密集的地方，建议后续用带登录态的浏览器或人工截图补齐。
3. **抖音只拿到文案标题**：抖音的"尺寸:40""52*52 板子可拼"是文案口径，不是严格参数。
4. **没有做用户访谈**：所有"建议"中的数值分档（8/12/20/32 色等）是**工程推导（⚪）**，需 A/B 验证。
5. 可继续追的线索：B 站「萬发发做手工」的"多少色合适"系列、`pixm.lat`（怪兽小拼豆）的实际算法、`Pindou.art` / `pixel-beads.com` / `beadscanvas.com` 三站的减色参数对比。
